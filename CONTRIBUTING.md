# Contributing

## Publish model

`main` is the consumer-facing branch. Anything merged to `main` is considered
published — there is no separate release, dev, or deploy branch. Downstream
consumers (rhiza-agents, skillkit, the demo's `uv tool install ../`, standalone
single-file copies) read from `main`, so every merge to `main` is a release.

Each `skills/<name>/SKILL.md` carries a `metadata.version` field in its YAML
frontmatter (nested under the top-level `metadata:` key per the Agent Skills
specification). That field is the authoritative identity of a published
skill and the value that downstream cache invalidation keys on. Scripts that
emit `weather_skills_history` carry a `_SKILL_VERSION` constant near the top of
the file; the version-bump workflow rewrites both the SKILL.md
`metadata.version` and the `_SKILL_VERSION` literal in lockstep, so
contributors never edit either by hand.

## PR workflow

1. Branch off `main`.
2. Open a PR back into `main`.
3. CI must pass (the `CI` workflow runs ruff format-check, ruff check, inline-dep
   validation, and a `--help` invocation per script).
4. Rebase onto `main` before merging — linear history is required.
5. Use the GitHub merge button (squash-merge or rebase-merge, per-PR choice).

Authors **must not** edit any `metadata.version` field by hand. The version
bump is fully owned by the `version-bump` workflow (see below).

## Version bumps

The `.github/workflows/version-bump.yml` workflow runs on every push to `main`.
It diffs the push range, identifies which `skills/<name>/` directories changed,
and emits ONE bump commit per workflow run that updates every affected skill
in lockstep. Each skill is versioned independently — they drift apart over
time — so the commit subject does not name any specific version. The commit
body enumerates each affected skill's before → after.

Commit shape:

```
release: bump skill versions [skip ci]

- skill-a: 0.3.1 -> 0.3.2
- skill-b: 1.2.0 -> 1.2.1
- skill-c: 0.1.4 -> 0.1.5

Auto-generated by .github/workflows/version-bump.yml in response to skill-directory changes in commit <sha>.
```

If only one skill changed, the body still uses the same bullet-list format
(one bullet). If no skills changed (e.g. a docs-only PR that touches files
outside `skills/<name>/`), the workflow exits cleanly and creates no commit.

The bump kind is read from labels on the merged PR:

| Label             | Bump kind   | Example       |
| ----------------- | ----------- | ------------- |
| `release: major`  | major       | 0.1.0 → 1.0.0 |
| `release: minor`  | minor       | 0.1.0 → 0.2.0 |
| (none, or other)  | patch       | 0.1.0 → 0.1.1 |

The same bump kind applies to every skill bumped within one workflow run, but
each skill's starting version is its own. Two skills bumped under a `release:
minor` PR will both gain a minor component, but the resulting versions are
independent — `skill-a` going from `0.3.1` to `0.4.0` and `skill-b` going from
`1.2.0` to `1.3.0` would land in the same bump commit.

Patch is the fall-through bump when no `release: major` or `release: minor`
label is present. There is no `release: patch` label — patch is not a
recognized value, it's simply what the workflow does by default.

The labels `release: major` and `release: minor` need to exist on the repo.
Set them up once via the GitHub UI (Settings → Labels) or via `gh label create`.

If a PR carries more than one `release:` label (e.g. both `release: minor` and
`release: major`), the highest precedence wins — `major` beats `minor` beats
`patch`. This matches the workflow's grep order in
`.github/workflows/version-bump.yml`.

The bump commit lands directly on `main` via the workflow's push step. The
`[skip ci]` marker in the bump-commit subject prevents the workflow from
re-triggering itself. The push step retries up to three times with a
`git pull --rebase origin main` between attempts, so a near-simultaneous merge
to `main` between checkout and push doesn't silently drop the bump.

Each push range is processed independently: if two PRs that both touch
`skills/foo/` are merged in close succession, each merge fires its own
workflow run and produces its own bump commit. The two bumps are sequential
commits on `main`, not a combined bump. That's intentional — each PR's labels
(and therefore its bump kind) are honored independently.

### Force-push to `main`

The bump workflow assumes a linear, fast-forward-only `main`. Force-pushing to
`main` is not a hard blocker (the workflow's push retry will rebase and try
again), but it eliminates a vector for spurious bumps where a force-push that
rewrites history can produce a confusing diff range against
`github.event.before`. Recommend disabling force-push to `main` under
Settings → Branches → Branch protection rules.

### Reverting a bad release

`git revert <bump-commit>` rolls SKILL.md (and `_SKILL_VERSION` literals
in scripts) back to their previous values, but consumers that already cached
the bad version under its old identity won't see the revert — same-identity
state stays cached. To truly roll back a release, do this:

1. Open a PR that reverts the bump commit (or directly revert it on `main` if
   branch protection allows).
2. In the same PR or a follow-up, push any change under
   `skills/<name>/` (a doc tweak, a no-op edit, anything the diff observes).
   That change re-triggers the version-bump workflow, which emits a fresh
   bump commit producing a version HIGHER than the bad one.
3. Downstream consumers keyed on `metadata.version` invalidate their cache
   and pick up the corrected state under the new identity.

Don't try to repeat the bad version. A same-version revert doesn't invalidate
downstream caches; a forward-bump does.

Equivalently, you can skip the revert and just land a forward fix — a new
commit that supersedes the bad release on top, which the workflow will bump
to a new version. This is simpler when the bad state is recoverable in-place.

## Branch protection settings (configured manually by the maintainer)

Configure these on `main` under Settings → Branches → Branch protection rules:

- **Require a pull request before merging**: on.
  - Require approvals: at least 1.
- **Require status checks to pass before merging**: on.
  - Required checks: the `ruff`, `inline-deps`, `discover`, and `script-help`
    jobs from `.github/workflows/ci.yml`.
- **Require linear history**: on. (Forces rebase-or-squash; blocks merge
  commits, so the bump workflow's view of `github.event.before..github.sha`
  remains a clean linear range.)
- **Do not allow merge commits**: on (i.e. disable the "Create a merge
  commit" merge button option).
- **Allow squash merging**: on.
- **Allow rebase merging**: on.
- **Restrict who can push to matching branches**: on. The allow-list contains
  only the `forecasting-skills-release-bot` GitHub App. No human user
  is on the allow-list — every human change reaches `main` through the PR
  flow. The App is the only identity that pushes directly to `main`, and it
  only does so to land the workflow's bump commits.
- **Enforce admins** (`enforce_admins: true`): on. Admin bypass is
  intentionally disabled so even repo admins go through the PR flow. The
  App is the sole direct-push identity.

  If the App is not in the allow-list, the bump push will fail with a
  non-fast-forward or protected-branch error and the workflow will exit 1
  after three retries.

## Required secrets

The `version-bump` workflow authenticates as a dedicated GitHub App
(`forecasting-skills-release-bot`) so its bump commit carries a bot
identity isolated from any human user. Each workflow run mints a short-lived
installation token via `actions/create-github-app-token@v2` from the App's
ID and private key. The token is used both for the `gh api` PR-label lookup
and for the `git push` that lands the bump commit.

A dedicated App (rather than the default `GITHUB_TOKEN`) is used for two
reasons:

1. Cross-workflow triggering — the default `GITHUB_TOKEN` is intentionally
   inert for cross-workflow triggering, so a push made with it cannot fire
   other workflows. An App-minted token can.
2. Identity isolation — the App's bot user is the only identity on the
   "Restrict who can push" allow-list for `main`, so direct pushes to `main`
   are limited to this one workflow.

The `[skip ci]` marker on the bump commit prevents the workflow from
recursing on its own push regardless of token.

Configure once at Settings → Secrets and variables → Actions:

- `RELEASE_BOT_APP_ID` — the numeric App ID, visible on the App's settings
  page at `https://github.com/settings/apps/forecasting-skills-release-bot`.
- `RELEASE_BOT_PRIVATE_KEY` — the full `.pem` contents of a private key
  generated for the App. On the App's settings page, scroll to "Private
  keys" → "Generate a private key"; the browser downloads a `.pem` file.
  Paste its full contents (including the `-----BEGIN ...-----` and
  `-----END ...-----` lines) into the secret value. Private keys are not
  recoverable after creation, so if the file is lost, generate a new key
  and rotate the secret.

### App setup (one-time)

The App is created once and reused. To recreate it from scratch:

1. Settings → Developer settings → GitHub Apps → New GitHub App.
2. Name: `forecasting-skills-release-bot`.
3. Homepage URL: any non-empty URL (the App is not user-facing).
4. Webhook: disabled (uncheck "Active"). The App has no event subscriptions.
5. Repository permissions:
   - `Contents: Read and write` — for the push step that lands the bump
     commit on `main`.
   - `Pull requests: Read-only` — for the `gh api .../commits/<sha>/pulls`
     lookup that reads the merged PR's labels.
   - `Metadata: Read-only` — required by GitHub for any App; every other
     permission depends on it being granted.
6. "Where can this GitHub App be installed?": "Only on this account".
7. Create the App, then on its settings page:
   - Note the App ID (numeric) shown under "About".
   - Generate a private key under "Private keys" and save the downloaded
     `.pem` file.
   - Install the App on this repo only (Install App → choose the repo).
8. Store the App ID as `RELEASE_BOT_APP_ID` and the `.pem` contents as
   `RELEASE_BOT_PRIVATE_KEY` under repo Settings → Secrets and variables
   → Actions.
9. Add the App to the `main` branch protection rule's "Restrict who can
   push to matching branches" allow-list.
